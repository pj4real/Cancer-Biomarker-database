## A. Concept and motivation

**1. What problem does CancerBioMap solve?**
It integrates biomarker, gene, protein, pathway, variant and publication data in one relational
database. For every biomarker–cancer association it shows *what evidence supports it*, how strong and
diverse that evidence is, and where evidence is missing or conflicting.

**2. What is a cancer biomarker? Which roles do you model?**
A measurable biological characteristic that indicates a normal or disease process or a response to
therapy. Five roles are modelled: *diagnostic* (detects or classifies disease), *prognostic* (outcome
regardless of therapy), *predictive* (benefit from a specific therapy), *risk* (susceptibility) and
*monitoring* (tracking disease over time). For example, KRAS mutation in colorectal cancer is
*predictive*: it predicts lack of benefit from anti-EGFR antibodies.

**3. Why store association per role rather than per biomarker–cancer pair?**
The evidence differs by role. HER2 in breast cancer is prognostic (Slamon 1987) and predictive
(Slamon 2001 trastuzumab trial). Scoring them together would mix unrelated evidence. The constraint is
`UNIQUE(biomarker_id, cancer_id, biomarker_role)`.

**4. What is the novelty, precisely?**
Not a new biological finding, and not a clinically validated score. It is an evidence-coverage
assessment that is *decomposable* (four inspectable components), *missing-data-aware* (unknown is
never zero; provisional and insufficient states) and *de-duplicated*, built into the relational
database together with a gap analysis. Expert-level systems such as CIViC and OncoKB assign
categorical evidence levels; this project complements them with a transparent coverage measure.

**5. How is your system different from CIViC or OncoKB?**
They are large expert-curated knowledgebases with evidence levels assigned by curators. CancerBioMap
is a teaching-scale integrated database whose distinguishing feature is the computed, explainable,
versioned coverage score and the gap flags derived from evidence *metadata*. It does not replace expert
interpretation.

## B. Database design

**6. Explain your ER model.**
Core entities: Biomarker, Cancer, Gene, Protein, Pathway, Variant and Publication. The association
entity `biomarker_cancer` (M:N between biomarker and cancer, with a role attribute) owns Evidence
(1:N) and EvidenceScore (1:N, one per scoring version). Junction tables (`biomarker_gene`,
`biomarker_pathway`, `gene_pathway`, `gene_protein`, `variant_association`) resolve the M:N
relationships with composite primary keys. Variant → Gene is N:1.

**7. Show your schema is in 3NF.**
Attributes are atomic (multi-valued facts are in junction tables). Junction tables contain only their
composite key, plus `annotation_source`, which depends on the full key (2NF). There are no transitive
dependencies: publication facts live only in `publication`, and evidence references it by FK (3NF).
Example of a violation we avoided: storing `journal` in `evidence` would make it depend on
`publication_id`, not on `evidence_id`.

**8. Why both a surrogate key and a unique natural key?**
Surrogate integer keys are stable, compact join keys. UNIQUE natural keys (`official_symbol`,
`accession`, `pmid`, `biomarker_code`) stop duplicates and let the importer upsert idempotently.

**9. What constraints enforce integrity?**
- FKs with deliberate actions: CASCADE for dependent rows (association → evidence), RESTRICT for
  master data (a cancer with associations cannot be deleted), SET NULL when a publication is removed.
- CHECK constraints for vocabularies (role, type, evidence type, consistency), years 1900–2100,
  positive genomic positions, and `pmid IS NOT NULL OR doi IS NOT NULL`.
- UNIQUE constraints on natural keys, on `(association_id, publication_id, source_name)` for evidence,
  and on `(association_id, scoring_version)` for scores.
SQLite enforces FKs only with `PRAGMA foreign_keys=ON`, which `app/database.py` sets on every connection.

**10. Why is `gene_pathway` separate from `biomarker_pathway`?**
Pathway membership is a fact about a gene, as stated by KEGG. The biomarker–pathway link is *derived*
from it. Storing both, with `annotation_source` naming the gene, keeps the provenance explicit.

**11. Which indexes did you create and why?**
On every FK column (join performance), on filter and sort columns (`biomarker.name`, `biomarker_type`,
`publication_year`, `evidence_type`, `overall_score`), and a composite `(cancer_id, biomarker_role)`
for the most common filter combination. UNIQUE constraints create indexes implicitly.

**12. How do migrations work?**
Alembic revision `0001_initial_schema` was autogenerated from the ORM models and reviewed.
`scripts/init_db.py` runs `upgrade head`. The PostgreSQL DDL file was produced with
`alembic upgrade head --sql` (offline mode). A test confirms the migration creates exactly the
tables in the models.

**13. Why does SQLite work if the target is PostgreSQL?**
SQLAlchemy abstracts dialect differences, and the analytics SQL uses only portable constructs (JOIN,
GROUP BY/HAVING, COALESCE, CASE, INTERSECT, LIMIT). For example, `ROUND(AVG(x), 1)` is avoided because
PostgreSQL has no `ROUND(double precision, int)`; rounding is done in Python.

## C. SQL

**14. Write a query for biomarkers shared between two cancers.**
`INTERSECT` of the two `biomarker_id` sets (catalogue Q8). Breast ∩ colorectal = HER2 amplification.

**15. Why LEFT JOIN in the "limited evidence" report?**
An INNER JOIN would drop associations with no evidence at all (CA 15-3), which are exactly the ones we
want to find.

**16. Why COUNT(DISTINCT e.publication_id)?**
One publication can back several evidence rows (for example, OlympiAD for BRCA1 and BRCA2). Counting
rows would inflate support.

**17. How do you prevent SQL injection?**
All queries are SQLAlchemy expressions or `text()` with bound parameters (`:cancer_a`). User input
is never interpolated into SQL. Report parameters are also type-checked before execution.

**18. Explain the self-join report.**
`biomarker_pathway bp1 JOIN biomarker_pathway bp2 ON bp1.pathway_id = bp2.pathway_id AND
bp1.biomarker_id < bp2.biomarker_id` pairs biomarkers in the same pathway. The `<` removes self-pairs
and mirrored duplicates.

## D. Evidence-support score

**19. State the formula and its components.**
`Score = 0.35P + 0.25D + 0.25T + 0.15C`. P = `100·log2(1+n)/log2(6)` (capped), D = `100·(1−0.5ⁿ)`,
T = `0.7·max + 0.3·mean` of the evidence-type rubric, C = `100·(supports + 0.5·mixed)/annotated`.

**20. Why logarithmic publication support?**
Diminishing returns: the second study adds more confidence than the twentieth, and a cap stops one
heavily studied biomarker from dominating.

**21. Why were these weights chosen? Are they validated?**
They are proposed project parameters reflecting a judgement that the volume and design of evidence
matter most. They are **not validated**, are configurable in `.env`, and are validated at startup to
sum to 1. Future work: sensitivity analysis.

**22. How do you handle missing data?**
A component with no observable input is NULL (unknown), never 0. If at least 50% of the weight is
observed, a *provisional* score is reported: `Σwᵢxᵢ / Σwᵢ` over observed components, with a clear
warning. Below that, the status is *insufficient* and no score is shown. Example: PTEN loss has no
consistency annotations, so it is provisional (coverage 85%). CA 15-3 has no evidence, so it is
insufficient.

**23. Why is zero publications "unknown" instead of 0?**
Absence of a record in *this* database is not evidence of absence in the literature. Scoring it 0
would misrepresent curation gaps as negative evidence.

**24. How do you avoid counting duplicates?**
Publications are de-duplicated by PMID/DOI, sources by normalised name, and evidence types by distinct
value. A unit test confirms duplicate rows leave the score unchanged.

**25. Is the score deterministic?**
Yes. `compute_score` is a pure function with no clock, randomness or I/O. Scores are stored with
`scoring_version`. A test runs it repeatedly and compares the outputs.

**26. Walk through a manual calculation.**
Three publications (RCT, cohort, genomic profiling), two sources, two "supports":
P = 77.37, D = 75, T = 0.7·95 + 0.3·80 = 90.5, C = 100 → 0.35·77.37 + 0.25·75 + 0.25·90.5 + 0.15·100
= **83.45** (`tests/test_scoring.py::test_manual_complete_case`).

**27. Can a high score mean a biomarker is clinically valid?**
No. It measures how much, how varied and how consistent the *recorded* evidence is. The UI and API
state this disclaimer explicitly.

**28. Give an example of conflicting evidence in your data.**
CEA / colorectal / *diagnostic*: the ASCO 2006 tumour-marker guideline does not recommend CEA for
screening, so it is annotated `conflicting`, while CEA *monitoring* is `supports`. PSA screening has
PLCO (no mortality reduction, `mixed`) and ERSPC (reduced mortality, `supports`).

## E. Data integrity and sources

**29. How did you ensure no citations were fabricated?**
Every PMID was checked against PubMed `esummary` (`scripts/fetch_pubmed.py`). This found 11
discrepancies in the initial list, which were corrected before import. Metadata (authors, journal,
year, DOI) comes from PubMed, not from memory.

**30. What else was verified?**
NCBI Gene IDs vs symbols, UniProt accessions (reviewed, human, correct gene), GRCh38 positions and
alleles of dbSNP variants (Ensembl), GDC project IDs, and KEGG pathway membership (KEGG REST), all
via official APIs.

**31. How does the importer prevent bad or duplicate data?**
Pydantic row models validate types, vocabularies, formats (UniProt accession regex, rsID, alleles,
chromosome) and cross-field rules. Duplicate keys within a file are rejected. A file is written
atomically: any error rolls back the whole file. Records are upserted on natural keys, so re-import
inserts nothing (tested).

**32. Why are KEGG evidence rows untyped?**
Membership of a gene in KEGG's disease map supports gene–cancer relevance but not a specific
biomarker role. Assigning an evidence type would overstate it, so the type stays unknown and is
flagged as a gap.

## F. Implementation

**33. Why FastAPI?**
Declarative validation with Pydantic, automatic OpenAPI/Swagger documentation, and good performance.

**34. How are errors handled?**
Custom handlers return `{"error": {code, message, details}}` with 400, 404, 422 or 500. Unhandled
exceptions are logged server-side and return a generic message, so no stack traces or SQL reach
the client.

**35. Are frontend filters applied in the browser?**
No. Every search, filter, sort and pagination parameter is sent to the API and executed in SQL. The
dashboard numbers are SQL aggregates.

**36. How is the network graph built?**
`/api/network` builds nodes and edges only from database relationships (associations, biomarker_gene,
gene_protein, biomarker_pathway, evidence → publication, variant_association). The frontend lays it out
with a deterministic force-directed algorithm, so the same data always gives the same picture.

**37. What did you test?**
51 backend tests (schema constraints, cascades, migration, import validation and idempotency, scoring
including manual cases, all major API endpoints, errors and CSV export) and 9 frontend tests (unknown
rendering, provisional warning, layout determinism).

## G. Critical reflection

**38. Main limitations?**
Small curated sample, uncalibrated weights, single-curator annotations, selection bias towards
landmark positive studies, and source independence approximated by name.

**39. How would you validate the score?**
Compare score rankings against expert evidence levels (for example, CIViC or OncoKB tiers) with rank
correlation, run a weight sensitivity analysis, and measure inter-curator agreement on annotations.

**40. How would you scale it?**
Run on PostgreSQL with full-text indexes, add batch ingestion from CIViC/PubMed with provenance,
precompute scores asynchronously on evidence changes, and add authentication for curators.
